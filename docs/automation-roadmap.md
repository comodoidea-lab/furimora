# 自動化ロードマップ — フリモーラ全機能の自動化とデスクトップ化

作成日: 2026-09-01 / 前提: [clone-entrypoints.md](clone-entrypoints.md)、[obscura-migration-report.md](obscura-migration-report.md)

## 出発点の事実確認

**フリモーラにはメルカリへの書き込み処理が 1 行も存在しない。**（2026-09-01 コード全体を確認）

外部への POST は 2 箇所だけ:

| 箇所 | 宛先 |
|---|---|
| `public/index.html:2127` | Google Drive（バックアップ） |
| `public/index.html:6870` | `/api/push-send`（Web Push） |

したがって現状は以下のとおり:

| 機能 | 実態 |
|---|---|
| 「自動値下げ」 | アプリ内の在庫データの価格を書き換え、期日にプッシュ通知を送るまで。メルカリ側の価格変更は人間の手作業 |
| Chrome 拡張の「10% 値下げ」 | 新価格をクリップボードにコピーするだけ |
| 「再出品」 | 貼り付け支援 UI。実際の削除・再出品は人間 |

**つまり書き込み自動化は「CDP から解放する」話ではなく、まだ一度も作られていない機能を新規に作る話。**

## 機能別の到達状況

| | 機能 | 状態 | 必要なもの |
|---|---|---|---|
| A | 商品情報取得 | ✅ **完了。ブラウザ不要** | — |
| B | クローン用データ作成 | ✅ **完了。ブラウザ不要** | — |
| C | ログイン維持 | ❌ 未着手 | 認証済みセッション |
| — | 自分の出品一覧 | ❌ 未着手 | 認証済みセッション（読み取りのみ） |
| D | 価格変更 | ❌ 未着手 | 認証済みセッション + 書き込み手段 |
| E | 出品操作 | ❌ 未着手 | 上記 + 画像アップロード |

A / B が完了しているのは `/api/mercari` が **DPoP 署名をサーバー側で生成し、認証なしで公開情報を取得できる**ため。
実測で 10/10 項目（[clone-entrypoints.md](clone-entrypoints.md) の同等性検証を参照）。

C 以降が残るのは、いずれも**ログイン済みセッション**を必要とするため。
`jp.mercari.com/robots.txt` も `/mypage/` `/sell/` `/transaction/` を Disallow としている。

## 2 つの route

### Route 1: 内蔵ブラウザ（推奨）

アプリの中に Chromium を持ち、ログインもフォーム操作もその中で完結させる。

```
ログイン（初回 1 回、人間が 2FA を通す）
  → セッションはブラウザの partition に残る
  → 以降は DOM 操作で価格変更・出品・削除
```

- **Electron を使うなら Chromium は同梱済み。内蔵ブラウザの追加コストはゼロ**
- 認証トークンの抽出・保管・更新が**不要**（セッションはブラウザが持つ）
- 画像アップロードはフォームへ `setInputFiles` するだけ
- プロファイル分離は `partition: 'persist:mercari'` の一行
- 弱点: **DOM 依存。メルカリの UI 変更で壊れる。逐次実行で遅い**

### Route 2: 認証付き API 直叩き

ログインで得たアクセストークンを保管し、非公開エンドポイントを DPoP 署名して呼ぶ。

- 速い・並列可・UI 変更に強い
- 弱点: 非公開エンドポイントの特定が必要。画像アップロードが多段で面倒。
  トークンの抽出・Keychain 保管・更新管理が必要。**そして初回ログインは結局ブラウザが要る**

### 判断

**Route 1 を採る。** Route 2 は手数が多いうえ、初回ログインでブラウザから逃れられない。
Route 1 なら同じブラウザで書き込みまで済む。

将来 Route 2 に寄せたくなった場合も、BrowserService / MercariService の層が分かれていれば
下だけ差し替えられる。

### Obscura について（決着済み）

閉じたのは「**Chromium ではない自作エンジンを内蔵する**」路線だけ。
Obscura はメルカリ商品ページを 25 秒待っても `loading-skeleton` のまま描画できず、
CDP の `Input.insertText` も未実装だった。Electron の Chromium は本物なのでこの問題は起きない。

## 目標構成

```
フリモーラ Desktop（Electron / macOS・Windows）
├── メインプロセス
│   ├── MCP サーバー      ← mcp/server.mjs をそのまま載せる（実装済み）
│   ├── ApplicationService ← UI と MCP の共通入口
│   ├── MercariService    ← セレクタとメルカリ固有ロジックを 1 箇所に集約（未実装）
│   └── BrowserService    ← Electron の webContents を操作（PoC のものを流用）
├── レンダラ 1: public/（今の UI。無改修）
└── レンダラ 2: 非表示の BrowserWindow（メルカリ専用・独立 partition）
```

**セレクタは必ず MercariService に集約する。** DOM 依存の脆さは消せないので、
壊れたときに直す場所が 1 箇所で済むかどうかが運用の寿命を決める。

## フェーズ

### フェーズ 1: 自分の出品一覧（読み取りのみ）← **完了（2026-09-01）**

`mercari_get_my_listings`。認証が要る最初の一歩だが**読み取りだけ**なので、
間違っても何も壊れない。ここで以下を作り切る。

- 内蔵 BrowserWindow の起動とセッション永続（`partition: 'persist:mercari'`）
- ログイン状態の判定（`checkLogin()`）
- ログインが切れていたらウィンドウを表示して人間に 2FA を通してもらう導線
- MercariService のセレクタ集約の型を決める

**ここを飛ばして価格変更から入ると、認証基盤と書き込みを同時に作ることになり切り分けができない。**

#### 完了時点の状態（次に再開する人向け）

実装は `mcp/src/browser-service.mjs` と `mcp/src/mercari-service.mjs`。main にマージ済み。

- 専用プロファイル `~/.furimora/chrome-profile` は**メルカリにログイン済み**。
  headless でもセッションが効くことを確認済み。切れていたら `mercari_login` を実行する
  （認証情報の入力は人間が行う。エージェントは入力しない）
- MCP ツール: `mercari_check_login` / `mercari_login` / `mercari_get_my_listings` /
  `furimora_reconcile_listings`
- 実測: 出品中 44 件を約 8 秒、売却済み 319 件を約 21 秒。取得率はタイトル・価格とも 100%
- 照合の実地確認: 在庫 106 件のうち 104 件一致、価格のズレ 2 件（¥1520 → ¥1518）、
  「売れているのに出品中のまま」は 0 件

メルカリ側 DOM の癖は `mcp/README.md` と `mercari-service.mjs` のコメントに全部書いてある。
**実データを通すまで出なかった不具合が 4 件あった**ので、フェーズ 2 でも実データ検証を必ず通すこと。

#### やり残し

- 在庫データの受け渡しが手動（設定画面でバックアップ JSON を保存 → `backup_path` で渡す）。
  ブラウザからのプログラム的ダウンロードは Chrome にブロックされる。
  Electron 版では在庫を直接読める形にしたい
- 照合結果をフリモーラの UI に出す部分は未着手（`public/js/reconcile.js` は
  純粋関数なのでブラウザ側だけで完結できる）

### フェーズ 3-a: **メルカリの下書きまで**（E を分割した前半）← **実装完了（2026-09-01）**

**出品はしない。メルカリの「下書き」を作るところで止める。**

段階が 3 つあることを利用する。

```
① フリモーラの下書き   既存（furimora_drafts。クローン機能がここまで作っている）
② メルカリの下書き     ← フェーズ 3 のゴール。まだ誰にも見えない
③ 出品する             人間が押す（フェーズ 4）
```

②で止めれば**破滅的な失敗が構造的に起こり得ない**。手間はほぼ変わらない
（フォーム入力も画像アップロードも自動化される）のに、誤った価格・写真・カテゴリで
公開されるという最悪の失敗だけが消える。

| | 直接出品 | 下書きまで |
|---|---|---|
| 価格・写真・カテゴリを間違えた | 公開されてしまう | 下書きなので誰にも見えない |
| 自動化される作業 | 全部 | **ほぼ全部** |

#### 実装（2026-09-01）

`mercari_create_draft`。**`dry_run` の既定は true。出品はしない。**
メルカリに自動保存が無いことを利用し、**確認モードでもフォーム入力とカテゴリー選択を実際に行う**。
そのためカテゴリーの経路が実在するかまで、保存せずに検証できる。

必須は **商品名・説明・価格・カテゴリー・商品の状態** の 5 つだけ。
画像とカテゴリー固有の属性は下書きには required ではないことを実データで確認済み。
**商品の状態には既定値を与えない**（推測させないため必須にした）。
配送の方法・発送元・発送日数はメルカリ側の既定値のままにする。

検証は `node check-draft.mjs`（**下書きを 1 件も作らない**）。詳細は `mcp/README.md`。

#### フェーズ 3-b: クローン元との接続（2026-09-01）

`mercari_prepare_draft_from_item`（商品URL → 下書きの引数）と
`mercari_resolve_category`（経路の解決）を追加した。**どちらも読み取りのみ。**

- `category`（`"A > B > C"`）は出品ツリーを実際にたどって末端まで解決する。
  届かなければその階層の**候補を返す**。末端を推測して勝手に選ぶことはしない
- `condition`（`"新品、未使用"`）は 1〜6 に対応づける。一致しなければ `null`
- **`price` は必ず `null` で返す**（クローン元の価格をそのまま使わせない）
- 人間が確定させるべき項目は `needsHuman` に列挙して返す

**新たに分かったこと**: 末端カテゴリーによっては `/sell/wizard`（製品情報の入力）へ飛ぶ。
任意の導線なので「出品画面に戻る」で素通りする。実測でゲーム・おもちゃ・グッズ >
キャラクターグッズ > その他 で発生した。**これも実データを通すまで出なかった。**

残っているのは以下。

- 画像つきの保存を実データで未検証（`image_paths` は実装済み・ガードのみ検証）。
  **書き込みを伴うので人間の承認が要る**
- 「商品の状態」を人間に確定させる UI 導線（フリモーラ側の作業）

#### 目指す入力の形

**ユーザーが渡すのは写真と価格（最低価格までのバッファ含む）だけ**にする。
残りは生成し、フリモーラ上で確認・修正してからメルカリの下書きへ送る。

```
写真 + 価格 → 下書き案を生成 → フリモーラで確認・修正 → メルカリの下書き → 出品（人間）
                                  ↑ ここで状態と発送方法を確定させる
```

確認をメルカリ側でなくフリモーラ側で行うのは、修正のしやすさのため。

#### 項目ごとの難易度（着手前に読むこと）

| 項目 | 難易度 | 備考 |
|---|---|---|
| 商品説明 | 易 | 既存のテンプレート機能と組み合わせる |
| 価格 | 易 | ユーザーが渡す。最低価格と利益計算は既存 |
| タイトル | 中 | 写真からの商品特定は当たり外れがある |
| 発送方法 | 中 | **設定済みの発送方法から選ばせる**（メルカリの全選択肢から推測しない）。サイズ・重量は写真だけでは分からない |
| カテゴリ | 難 | メルカリのカテゴリツリーは 4〜5 階層と細かい |
| **商品の状態** | **難** | 写真から傷の有無を判定する信頼性は低い |

**状態と発送方法だけは必ず人間が確定させる。** この 2 つは間違えると実害が出る
（状態を良く見積もる → 取引トラブル。発送方法を誤る → 送料超過で赤字、または発送不能）。
生成時は**保守的な側（状態は悪め）を既定**にする。

#### 出品フォームの調査結果（2026-09-01・書き込みなし）

`/sell` は出品ホーム。実フォームは **`/sell/create`**、下書き一覧は **`/sell/drafts`**。

**`下書きに保存する`（`[data-testid="save-draft"]`）が存在することを確認した。**
Web から下書きを作れるので、出品せず下書きで止める設計は成立する。

素直に扱えるもの（セレクタは `mercari-service.mjs` の `SELECTORS.sell` に記録済み）:

| 項目 | 要素 |
|---|---|
| 画像 | `[data-testid="photo-upload"]` — `input[type=file]` `accept=image/*` `multiple`。`setInputFiles` が使える |
| タイトル | `input[name="name"]` |
| 説明 | `textarea[name="description"]` |
| 価格 | `[data-testid="price-text-input"]` |
| 送料負担 / 発送元 / 発送日数 | 素の `<select>`（`shippingPayer` / `shippingFromArea` / `shippingDuration`） |

##### ピッカー3種は解決した（当初「残る山」としていた箇所）

コンテナの DIV が押せなかったのは事実だが、**その内側に本物の `<a href>` があった。**
ピッカーはモーダルではなく**別ページへの遷移**である。

| ピッカー | 遷移先 |
|---|---|
| カテゴリー | `/sell/categories` |
| 商品の状態 | `/sell/conditions` |
| 配送の方法 | `/sell/shipping_methods` |

実機で確定した挙動:

- **ピッカーへ遷移してもフォームの入力は消えない**（戻ると保持されている）
- **自動保存は起きない。** `save-draft` を押さない限り下書きは 1 件も作られない
  （`/sell/drafts` の件数が前後とも 0 件であることを確認）
- カテゴリーは中間階層が `<a href="/sell/categories?category_id=N">`。
  **末端は `merActionRow` 内の `<button>`。** 同じ文言の `<a href="/sell/create">` が
  並んでいるが、そちらを押しても選択は反映されない（実測で反映されなかった）。
  1 つの階層に中間リンクと末端ボタンが混在することがある
- 商品の状態は `[data-testid="condition-1-row"]`〜`condition-6-row` の 6 択。
  番号が大きいほど状態が悪い。**保守的な既定は大きい番号側**
- 配送の方法は**既定で「ゆうゆうメルカリ便」が入っている**。複製ケースでは触らずに済む

##### 新たに分かった注意点（こちらが次の山）

- **カテゴリーを確定すると要素が後から生える。** ブランド欄（`brand-link`）と、
  カテゴリー固有の属性セレクト（`select[name^="dynamicAttributes."]`）。
  実測でレディース>トップス>シャツ・ブラウス>半袖 に 6 本生えた。
  **下書き保存に必須かどうかは未確認**
- **AI 出品サポート（`ai-listing-toggle`）が既定で ON。**
  写真から商品名・説明文・価格を自動で書き込むため、こちらの入力と衝突しうる。
  画像アップロード後に値が上書きされていないか必ず読み直すこと

#### 下書き保存の実データ検証（2026-09-01・人間の承認のもと 1 件だけ作成）

`save-draft` を実際に押して、下書きが作れることと必須項目を確かめた。

| 確かめたこと | 結果 |
|---|---|
| `dynamicAttributes`（カテゴリー固有の属性 6 本） | **すべて空でも保存できる。下書きには必須ではない** |
| 画像 | **なしでも保存できる**（一覧では NOIMAGE と表示される） |
| タイトル・説明・価格・カテゴリー・商品の状態・配送の方法 | すべて保持された。開き直して確認済み |

- `save-draft` を押すと `/mypage/drafts` へ遷移する（`/sell/drafts` は転送される）
- 下書きの実体は **`/sell/draft/<draftId>`**。開き直して編集できる
- 下書き編集ページのボタンは 3 つ:
  `list-draft-button`（出品する）/ `overwrite-draft`（上書き保存する）/ `delete-draft`（削除する）。
  **`list-draft-button` はフェーズ4まで押さない**（`SELECTORS.draft.dangerousButtons` に記録済み）

つまり **3-a の必須入力は「タイトル・説明・価格・カテゴリー・商品の状態」だけ**で、
画像と属性は後から人間が足せる。想定より軽い。

#### SELECTORS を evaluate へ渡す際の制約（ここで一度壊した）

`SELECTORS` は `browser.evaluate(fn, SELECTORS)` でページへ丸ごと渡している。
**そのため SELECTORS の値は直列化可能なものに限る。**
関数や `RegExp` を入れると `updatePrice`（フェーズ2）まで巻き添えで壊れる。
組み立てが要るものは `categoryBranchLink()` / `conditionRow()` / `parseDraftId()` のように
SELECTORS の外へ出すこと。

#### フェーズ 3-c: 実写真での検証と、順序の是正（2026-09-01）

実写真 6 枚で下書きを 1 件保存し、**実データでしか出ない不具合を 5 件踏んだ**。

| 踏んだもの | 内容 |
|---|---|
| AI 出品サポートのウィザード | 画像を渡すとモーダルが開き `body` が `position:fixed` に。閉じないとフォームは一切押せない。②でカテゴリーを推測してくる画面は**スキップする** |
| 画像枚数の数え違い | DnD で行が DOM に二重に現れ、6 枚を 12 枚と数えた |
| スクロール | 画像でフォームが伸び、Playwright の自動スクロールでは押せない要素が出る |
| 改行コード | 複製元は CRLF、`textarea` は LF。入力側を LF に揃えないと照合が必ず落ちる |
| 配送の方法 | ラジオを選ぶだけでは反映されない。**「更新する」を押して初めて確定する** |

ガードは正しく働き、いずれも**保存せずに中断**した（`IMAGE_COUNT_MISMATCH` / `FILL_FAILED`）。

- `furimora_list_drafts` / `mercari_prepare_draft_from_furimora_draft` を**正規の順序**とする
- `mercari_prepare_draft_from_item` は「フリモーラ側の確認を挟まない経路」と位置づけ直した

フリモーラの下書きは localStorage（`furimora_drafts`）にあり、MCP からは直接読めない。

##### 実データのバックアップで見つかったこと（2026-09-01）

#### 下書きの保持件数を 150 件にした（2026-09-03）

`furimora_drafts` は `unshift` してから `slice(0, N)` するので、超えた分は**最古から黙って消える**。
実データは 6/10・9/1・9/2 とも ちょうど 50 件で、**すでに上限に張り付いていた**。
「すべての出品をクローン下書き経由で作業する」運用と正面から衝突するため引き上げた。

##### 効いてくる上限は localStorage ではなく Firestore

最初 localStorage の 5 MB で見て「500 件でも余裕」と見積もったが**誤り**だった。
同期は `FURIMORA_SYNC_KEYS`（13 キー）を **`users/{uid}/app/state` の 1 ドキュメント**へ
まとめて書く。**Firestore のドキュメント上限は 1 MiB** で、こちらが 5 倍厳しい。
（`furimora_items` は別コレクションへ差分同期されるので、この枠には入らない）

実測（`furimoraMeasureSyncPayload()` と手計算が 5 バイト差で一致）:

| 下書き | state ドキュメント | |
|---|---|---|
| 50 件（旧） | 309 KB | 29.5% |
| **150 件（新）** | **594 KB** | **56.6%** |
| 300 件 | 1,020 KB | 97.3% ⚠ |
| 500 件 | 1,589 KB | ❌ 超過 |

下書き 1 件 ≒ 2,844 bytes（画像は URL 保持で base64 ではない）。
同居する `furimora_schedule`（87 KB）と `furimora_activities`（75 KB）も増えるので、
下書きだけで枠を使い切らない 150 件を採った。**増やすときは必ず実測してから決めること。**

##### 超過を検知できるようにした

- `furimoraMeasureSyncPayload()` — push の前に実サイズを見積もる。
  **1 MiB を超えるなら書きに行かず手前で止める**（`reason: 'too_large'`）。
  8 割を超えたら警告（1 セッション 1 回だけ）
- `furimoraIsDocTooLargeError()` — 超過は Firestore では `resource-exhausted` ではなく
  **`invalid-argument`** で返るため、既存の `furimoraIsQuotaError()` では拾えなかった。
  「上限リセット待ち」ではなく「データを減らす」必要があるのでメッセージを分ける
- バッジは `furimoraSyncBadgeLabel()` で サイズ超過 / 上限到達 / 失敗 を出し分ける

**未検証**: 実際に 1 MiB を超える push を Firestore に投げての確認はしていない
（本番データを壊さずに再現する手段が無いため）。判定関数とメッセージはブラウザ上で
4 パターン（超過・invalid-argument・quota・その他）を通して確認済み。

### フェーズ 0: Electron 化 ← **やる（2026-09-03 決定）**

#### 決め手は「制御権」であって使い勝手ではない

外部の Chrome プロファイルを使うかぎり、**キャッシュ方針もウィンドウ方針も同期の書き手の数も
Chrome 側の持ち物であって、こちらのものにならない。** 実測（2026-09-03）:

| | |
|---|---|
| `~/.chrome-mercari-automation` | **881 MB**（値下げルーティン用） |
| `~/.furimora/chrome-profile` | 137 MB |
| 881 MB の内訳 | Cache 308 / Code Cache 198 / Service Worker 120 / IndexedDB 78 = **704 MB がキャッシュ類** |

Cookie の実体はごく僅かで、残りは Chrome が勝手に貯めた派生データ。消しても同じだけまた貯まる。

```js
// ~/.claude/skills/playwright-ops/lib/browser.mjs:266
headless: options.headless ?? false,       // 既定で headful
```
```xml
<!-- com.comodoidea.mercari-cdp.plist -->
<key>RunAtLoad</key><true/>                 <!-- ログイン時 -->
<key>StartCalendarInterval</key>            <!-- 毎朝 09:00 と 09:30 -->
<key>ProcessType</key><string>Interactive</string>
```

**設計としてそうなっている。** 前面に出るのは不具合ではなく仕様。

Electron なら両方こちらの持ち物になる。`session` を握れるのでキャッシュを持たない構成にできる。
`BrowserWindow` を `show: false` で作れば、**そもそも前面に出てくる概念が無い。**

同じ理屈が同期にも効く。`users/{uid}/app/state` は 1 ドキュメントで、競合に負けた側は
`furimoraApplySyncPayload(payload, /* replaceLocal */ true)` で同期キーを消してクラウド版に
置き換える。**エージェント用に 2 人目の書き手を足す設計は、いつか必ずデータを飛ばす。**
Electron が「デスクトップのフリモーラそのもの」になれば書き手は 1 人のままで済む。

## リスク

**書き込みの失敗は読み取りの失敗と質が違う。**

- 読み取りが壊れる → 取得できなくて困る、で済む
- 書き込みが壊れる → **実際の出品が誤った価格になる、意図しない出品が作られる**

対策として、フェーズ 2 以降は必ずドライランを先に作り、実行前に差分を人間へ提示する。

規約面のリスクは読み取りより高い領域に入る。既に `/api/mercari` で非公式 API に依存しているとはいえ、
書き込み自動化は一歩踏み込むことになる。**判断はトモヤさん本人のもの。**
